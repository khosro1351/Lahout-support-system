روی پروژه «سامانه حمایت همیاران لاهوت» در Repository فعلی کار کن.

این مأموریت، بازطراحی و تکمیل نهایی «ارزیابی جامع خانواده» و «موتور امتیازدهی» است.

هدف این است که پنج حوزه ارزیابی با یک منطق واحد، کوتاه، قابل فهم، کم‌تایپ و تصمیم‌محور اجرا شوند و کل خانواده فقط یک ارزیابی واحد، یک Submit، یک Return و یک Approval داشته باشد.

این Specification محتوای نهایی این مرحله است.

==================================================
0) قواعد اجرایی
==================================================

- فقط روی branch فعلی staging کار کن.
- main دست‌نخورده بماند.
- Push انجام نده.
- در پایان Commit محلی و Commit hash بده.
- سند راهبردی پروژه مرجع معماری است.
- تغییرات را روی Infrastructure موجود انجام بده و سیستم موازی نساز.
- Document/Upload Pipeline جدیدی که در مأموریت قبل تکمیل شده حفظ و reuse شود.
- تاریخ‌های UI شمسی باشند.
- RTL و Responsive حفظ شود.
- View و Edit از هم متمایز بمانند.
- Permission / Audit / History حفظ شوند.
- Submitted/Approved Snapshotهای تاریخی نباید بازنویسی شوند.
- داده پایه Family/Member از Assessment Snapshot جدا بماند.
- سن فقط از DOB محاسبه شود.
- Offline Field Mode در این مأموریت خارج از Scope است.
- شورا، حمایت‌ها، تأمین مالی و سایر ماژول‌های خارج از ارزیابی در این مأموریت توسعه داده نشوند.

قبل از کدنویسی فقط Preflight کوتاه و هدفمند انجام بده:
- schema/model فعلی assessment
- livelihood
- health
- family/member base data
- current scoring
- submit/return/approve
- snapshot/history
- permission/audit
- document linkage
- tests

Preflight را به یک مأموریت جدا تبدیل نکن.

==================================================
1) اصل معماری: یک ارزیابی جامع، نه پنج ارزیابی
==================================================

پنج حوزه:

1. معیشت و اقتصاد
2. سلامت و درمان
3. مسکن
4. آسیب‌پذیری ویژه
5. آموزش

پنج Assessment مستقل نیستند.

همه آنها Sectionهای یک:

FamilyAssessment / FamilyAssessmentVersion

هستند.

Workflow کل ارزیابی:

Draft
→ Final Review
→ Submitted
→ Approved

یا:

Submitted
→ Returned
→ اصلاح
→ Resubmitted
→ Approved

فقط یک Submit برای کل ارزیابی وجود داشته باشد.
فقط یک تصمیم Manager برای کل ارزیابی وجود داشته باشد:
- Approve
- Return for correction

Submit/Approve/Return مستقل برای هر حوزه حذف شود.

Manager در Return بتواند Comment را به:
- حوزه
- بخش
- سؤال/مورد مشخص

متصل کند تا سرگروه بداند دقیقاً چه چیزی نیازمند اصلاح است.

اما Workflow همچنان Workflow واحد Family Assessment باشد.

==================================================

هنگام Submit، کل وضعیت ارزیابی به‌صورت یک Snapshot واحد Freeze شود:

- داده پنج حوزه
- Applicable domains
- raw domain scores
- raw total

- normalized score
- need level
- alerts/urgencies
- summaries
- documents مرتبط
- submittedBy

نسخه Submitted نباید مخفیانه قابل ویرایش باشد.

در Return:
- نسخه Submitted تاریخی حفظ شود.
- اصلاحات روی Working Revision/Draft قابل Audit انجام شوند.
- Resubmit یک وضعیت قابل مقایسه با نسخه قبلی ایجاد کند.

Approved Snapshot immutable باشد.

3) فلسفه مشترک فرم‌ها
==================================================

اصل:

«کمترین تعداد سؤال لازم + بیشترین تصویر تصمیم‌پذیر از خانواده»

بنابراین:

- تا حد ممکن Option-based باشد.
- «سایر» فقط در صورت انتخاب، Text کوتاه باز کند.
- سؤال شرطی فقط زمانی نمایش داده شود که موضوعیت پیدا کند.
- کاربر مجبور نشود گزینه نامرتبط را فقط برای Completeness ثبت کند.
- سؤال‌هایی که از Base Data قابل استخراج‌اند دوباره پرسیده نشوند.
- اصطلاحات «کم/متوسط/زیاد» بدون معنای عملیاتی استفاده نشوند.
- «نامشخص» با «ندارد» و «ثبت‌نشده» یکی نباشد.

4.4 فشار هزینه‌های ضروری — 0 تا 5

- سایر

- ندارد → 0
- دارد ولی قابل مدیریت است → 1

- قرض
- درمان
- قبوض
- آموزش
- سایر

- نامشخص

- سایر

9) Applicable Domain / N/A / Normalization
==================================================

مفاهیم زیر کاملاً جدا باشند:

- 0 Score
- N/A
- ندارد
- نامشخص
- ثبت‌نشده

Applicable:

- معیشت: همیشه
- سلامت: همیشه
- مسکن: همیشه
- آسیب‌پذیری: همیشه
- آموزش: فقط در صورت وجود عضو مشمول

Raw Score =
مجموع Score حوزه‌های Applicable

Applicable Maximum =
مجموع Max حوزه‌های Applicable

Normalized Score =
(Raw Score / Applicable Maximum) × 100

مثال:

آموزش N/A

Applicable Maximum =
30 + 20 + 20 + 15 = 85

Raw Score = 51

Normalized =
51 / 85 × 100 = 60

محاسبه روی Precision واقعی انجام شود.

در Snapshot ذخیره شود:

- domainRawScores
- applicableDomains
- rawTotal
- applicableMaximum
- normalizedScore

Classification روی مقدار نرمال‌شده قبل از Round نمایشی انجام شود.

==================================================
10) سطح نیاز A / B / C / D
==================================================

بعد از Complete شدن Assessment، سیستم خودکار Need Level تولید کند.

امتیاز بالاتر = نیاز بیشتر.

Threshold قطعی:

A:
Normalized Score >= 75

B:
50 <= Score < 75

C:
25 <= Score < 50

D:
0 <= Score < 25

اگر Assessment ناقص یا دارای Blocking Unknown باشد:

Need Level = نامشخص / Not yet classified

سیستم همزمان نمایش دهد:

- امتیاز نهایی
- سطح نیاز

مثال:

68/100
سطح نیاز B

Need Level وضعیت کلی خانواده است و با Urgency یکی نیست.

==================================================
11) Urgency / Alert Engine در ارزیابی
==================================================

یک خانواده ممکن است:
- A و بدون هشدار فوری
یا:
- B و دارای هشدار بحرانی

داشته باشد.

سطوح عملیاتی:

1) نیازمند توجه
2) فوری
3) بحرانی

هیچ Alertی نیز یک وضعیت معتبر است.

Default deadline:

نیازمند توجه:
حداکثر 7 روز

فوری:
حداکثر 72 ساعت

بحرانی:
همان روز / حداکثر 24 ساعت

Deadlineها در یک Configuration مرکزی باشند، نه پراکنده در UI.

==================================================
14) Triggerهای Alert
==================================================

Alert فقط از وضعیت‌های واقعاً عملیاتی ساخته شود.

حداقل Ruleهای زیر:

بحرانی:
- Health: عدم دریافت درمان ضروری همراه با خطر جدی
- Housing: فاقد سکونت پایدار همراه با نیاز فوری یا خطر آنی
- Vulnerability: خطر فوری برای کودک/سالمند/فرد وابسته
- هر وضعیت دیگری که در داده به‌طور صریح «بحرانی» ثبت شده است

فوری:
- Housing: خطر جدی تخلیه/جابه‌جایی
- Vulnerability: نیازمند اقدام سریع
- Health: نیازمند درمان ولی درمان مؤثر دریافت نمی‌شود، بدون Trigger بحرانی
- Livelihood: وضعیت بحرانی هزینه‌ای/تعهدی که نیازمند اقدام سریع است
- Education: ترک تحصیل/عدم ثبت‌نام یا خطر جدی ترک تحصیل در صورت نیاز به اقدام

نیازمند توجه:
- وضعیت قابل توجهی که Action فوری/بحرانی نیست ولی نیاز به Follow-up دارد.

یک Source Condition نباید در هر Re-render هشدار جدید بسازد.

Alert باید idempotent باشد.

وقتی علت Source برطرف شد:
Alert طبق Rule مناسب resolve/close شود و History حفظ شود.

## تکمیل مصوبه: مشمولیت آموزش

عضو فعال در یکی از این حالت‌ها مشمول است: سن ۶ تا ۱۸ سال تمام فارغ از وضعیت تحصیل؛ در هر سن، در حال تحصیل/دانش‌آموز/دانشجو؛ یا سن ۶ تا ۲۴ سال تمام با ترک تحصیل/ثبت‌نام‌نشده/در معرض ترک تحصیل یا غیبت شدید. صرف سابقه ترک تحصیل برای فرد ۲۵ ساله و بالاتر بدون تحصیل فعلی کافی نیست.

نبود DOB به‌تنهایی Blocking نیست؛ وضعیت تحصیلی روشن مبنای تعیین است. اگر DOB و وضعیت تحصیل هر دو نامعلوم یا ثبت‌نشده باشند، مشمولیت نامشخص و نیازمند تکمیل اطلاعات پایه است؛ این فقدان داده مجوز N/A نیست. آموزش فقط در صورت نبود عضو فعال مشمول بر مبنای اطلاعات موجود N/A می‌شود. سن فقط از DOB محاسبه می‌شود؛ سن دستی قدیمی در تعیین مشمولیت استفاده نمی‌شود.
