# تثبیت UI عمومی و پنل پشتیبان فنی

مبنا: `4b0e36cc33c45b4e08aa7805378cc1cf0e064001` روی همان Repository و شاخه `staging`. کار فقط محلی است؛ main تغییر نکرده و Push انجام نمی‌شود.

## صفحات و اجزای رابط

- `/technical`: خوشامد، چهار کارت واقعی وضعیت فنی، کارت‌های آزمایش نقش و دسترسی به کاربران و تاریخچه.
- `/technical/simulation`: صفحه مستقل آزمایش همان پنج نقش موجود.
- `/technical/health`: وضعیت API، اتصال PostgreSQL، نسخه واقعی بسته، محیط، زمان بررسی و دکمه بررسی مجدد. در خطای دریافت، کارت سبز موفق قبلی نمایش داده نمی‌شود. پایش خطای فنی اخیر هنوز «در مرحله بعد» است.
- `/technical/users`: تب کاربران نسخه جاری و تب حساب‌های توسعه/قدیمی، پنج فیلتر و Badge نقش‌ها.
- `/technical/audit`: کاربر واقعی، نقش مؤثر، عنوان فارسی رویداد، وضعیت ثبت، حالت آزمایش و زمان؛ کد فنی رویداد داخل جزئیات قابل بازشدن است.
- Login، Header، Sidebar، انتخاب نقش و Footerهای دارای برند: عنوان رسمی «کانون مهربانی همیاران لاهوت».

Screen، WorkspaceFrame، GuideFrame، Field، useData، جدول قابل اسکرول، کارت‌ها و Gridهای RoleWorkspace فعلی reuse شده‌اند. فایل `TechnicalWorkspace.tsx` بخش‌های فنی را از فایل بزرگ RoleWorkspace جدا و با همان الگوی فعلی رندر می‌کند. اجزای محلی HealthCards، SimulationCards، Badge و Mark و کمک‌تابع مشترک rolePresentation اضافه شده‌اند؛ Design System یا ساختار پروژه مستقل ساخته نشده است.

Sidebar راست شامل داشبورد فنی، آزمایش نقش‌ها، سلامت سامانه، کاربران و نقش‌ها، رویدادها و تاریخچه است. «پایش خطاهای فنی» و «پشتیبان‌گیری و مصرف منابع» غیرقابل کلیک و دارای Badge «در مرحله بعد» هستند. همه صفحات فارسی و RTL باقی مانده‌اند؛ Username و کد فنی در bdi/LTR هستند.

## Home و Back

خانه از `effectiveRole` گرفته می‌شود: `/technical`، `/guide`، `/executive`، `/leader`، `/helper` یا `/council`. فهرست نقش‌های قابل انتخاب با نقش فعال جمع نمی‌شود.

بازگشت براساس Parent مشخص است: پرونده معیشت به `/workspace/livelihood`؛ پرونده خانواده مشترک به `/workspace/groups`؛ ارزیابی خانواده به پرونده؛ جزئیات گروه به فهرست گروه‌ها؛ جزئیات افراد/درخواست دسترسی/مصوبه به فهرست مربوطه؛ صفحات سطح اول به Dashboard نقش فعال. Breadcrumb و returnTo معتبر فهرست خانواده‌های همیار شاهد حفظ شده‌اند. Parent دلخواه از history.state مبنای لینک قرار نمی‌گیرد.

Redirect قدیمی `/executive/permissions` و جزئیات آن به `/executive` اصلاح شده؛ `/guide/coordination` بازنشسته به Dashboard نقش فعال بازمی‌گردد. `/forbidden` برای ورود واقعی به مسیر غیرمجاز حفظ شده و لینک خروج از آن Dashboard نقش فعال است.

در Simulation، Home/Back نقش شبیه‌سازی‌شده را حفظ می‌کنند. فقط دکمه مستقل «بازگشت به پنل پشتیبان فنی» از حالت آزمایش خارج می‌شود؛ خروج از حساب همچنان نشست را خاتمه می‌دهد. Banner هویت واقعی و نقش مؤثر باقی است.

## آزمایش نقش و گروه

Dropdown عمومی حذف شده است. انتخاب سرگروه یا همیار، انتخاب گروه را در همان کارت باز می‌کند. تا انتخاب گروه، ورود Disabled و علت آن مشخص است. سه نقش سازمانی به انتخاب گروه نیاز ندارند.

داده گروه‌های این انتخاب از گروه‌های ACTIVE با codeهای `V100-TEST-G1` تا `V100-TEST-G5` تهیه می‌شود؛ عنوان نمایشی ساده «گروه ۱» تا «گروه ۵» است. گروه‌های قدیمی حذف یا تغییرنام نشده‌اند و مجوزهای API آزمایش نقش تغییر نکرده‌اند. در پایگاهی بدون این Seed، پیام نبود گروه جاری نمایش داده می‌شود؛ گروه خیالی یا جایگزین Legacy انتخاب نمی‌شود.

## کاربران، نقش‌ها و Audit

نمای جاری شامل ۱۹ حساب سناریوهای نسخه جاری به‌علاوه Aseman و TechSupportDev است: ۲۱ حساب در داده توسعه فعلی. حساب‌های شناخته‌شده CouncilDev، ExecutiveDev، LeaderDev، HelperDev، MultiRoleDev و ReviewLeader/ReviewHelper/ReviewCouncil در تب Legacy نمایش داده می‌شوند. این دسته‌بندی فقط نمایشی است و مجوز، Password، وضعیت ACTIVE یا انتصاب هیچ حسابی تغییر نمی‌کند.

نوع حساب: آزمایشی برای حساب‌های Development شناخته‌شده فعلی، توسعه قدیمی برای Legacy، و عملیاتی برای دیگر حساب‌ها. فیلترها: نام/Username، نقش، گروه، وضعیت واقعی حساب، نوع حساب. نقش‌های چندگانه جداگانه Badge دارند؛ شاهده بنفشی مدیر اجرایی و عضو شورای کانون است. حساب Aseman با عنوان خنثی «حساب همیار شاهد» نمایش داده می‌شود، چون نام ذخیره‌شده آن عنوان قدیمی نقش بوده؛ نام شخص تازه‌ای اختراع نشده است. کلید `SUPREME_GUIDE` و داده اصلی دست‌نخورده‌اند.

کاربران همچنان فقط‌خواندنی‌اند؛ ساخت/ویرایش کاربر و تغییر Role با دکمه نمایشی فعال وانمود نشده است. عملیات جدول «در مرحله بعد» دارد. Audit همان ۱۰۰ رویداد اخیر واقعی را می‌خواند؛ برای Request Attempt وضعیت «درخواست ثبت‌شده» نشان داده می‌شود و موفقیت عملیات فرض نمی‌شود. برای رخداد بدون نقش مؤثر، «ثبت نشده» مجاز است. رویداد Simulation نقش مؤثر و هویت واقعی را حفظ می‌کند.

## فونت و Branding

از ZIP ارائه‌شده توسط کارفرما `Liana-v1.0-Pro.zip` فقط دو فایل Variable WOFF2 استخراج شد:

- `src/assets/fonts/Liana-VF.woff2`، اندازه ۵۴۷۶۸ بایت.
- `src/assets/fonts/Liana-FD-VF.woff2`، اندازه ۵۳۰۱۶ بایت.

`src/fonts.css` با font-display:swap و وزن متغیر ۱۰۰ تا ۹۰۰ استفاده می‌شود. نسخه FD با unicode-range فقط برای ارقام لاتین، عربی و فارسی در متن عمومی اولویت دارد؛ حروف فارسی از Liana معمولی می‌آیند. bdi، code، pre و dir=ltr از Liana معمولی برای حفظ ظاهر کد/Username استفاده می‌کنند. خود مقدار داده، نوع عدد و پردازش Backend تغییر نمی‌کند.

فونت‌ها داخل Build بسته‌بندی می‌شوند و وابسته به نصب فونت روی ویندوز یا اینترنت نیستند. SOURCE.json مسیر داخل ZIP و SHA-256 هر فایل را ثبت می‌کند. فایل‌های TTF، نسخه Soft، فایل‌های نمایشی ZIP و اسکریپت‌های همراه آن وارد پروژه نشده‌اند. **Liana دیگر Deferred نیست.**
