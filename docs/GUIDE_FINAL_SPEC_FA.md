پروژه: سامانه جامع مدیریت حمایت کانون مهربانی همیاران لاهوت
مرحله فعلی: بازبینی اساسی و نهایی نقش «راهبر عالی / SUPREME_GUIDE»

این کار ادامه همان Repository و نسخه فعلی پروژه است. پروژه را از نو نساز و معماری موجود را بی‌دلیل جایگزین نکن. ابتدا وضعیت فعلی Source، Database، Migrationها، Seedها، APIها، تست‌ها و صفحات نقش SUPREME_GUIDE را کامل بررسی کن و سپس تغییرات زیر را روی همان ساختار اعمال کن.

اصل بسیار مهم:
هدف این مرحله ساخت یک داشبورد اداری یا سیستم مجوزدهی نیست. راهبر عالی نقش «راهبری، مشاهده کلان، نظارت و مدیریت ساختارهای اصلی» را دارد و نباید به مدیر اجرایی روزمره تبدیل شود.

1. قواعد عمومی و غیرقابل مذاکره

- همه متن‌های قابل مشاهده برای کاربر باید کاملاً فارسی باشند:
  عنوان صفحات، دکمه‌ها، فیلترها، وضعیت‌ها، Tooltipها، Empty Stateها، History، پیام‌های خطا و موفقیت، Enumها و Event Labelها.
- Enumهای Backend می‌توانند انگلیسی بمانند، اما مقادیری مثل:
  ACTIVE
  OPEN
  CRITICAL
  FAMILY_TRANSFERRED
  health
  housing
  education
  livelihood
  vulnerability
  و مشابه آنها هرگز خام در UI نمایش داده نشوند.
- تمام Seed Data مربوط به افراد کانون و اعضای خانواده‌ها با اسامی و نام‌خانوادگی‌های فارسی، طبیعی و مرسوم تولید شود.
- ساختار خانواده‌های Seed واقعی و متنوع باشد: زن/مرد، سن‌های مختلف، نسبت خانوادگی متفاوت و وضعیت‌های متفاوت ارزیابی.
- تاریخ‌های UI فارسی و یکنواخت باشند.
- UUID، JSON خام، Source ID، Debug Data و شناسه‌های فنی در UI عادی نمایش داده نشوند.
- هیچ داده فعلی Database حذف یا Reset نشود.
- Migrationها additive و امن باشند.
- History و Audit موجود حفظ شوند.
- تست‌های فعلی نباید خراب شوند؛ برای تغییرات جدید تست‌های لازم اضافه شوند.
- هدف فقط عبور تست نیست؛ Workflowها باید با مرورگر واقعی نیز بررسی شوند.

2. ساختار نهایی داشبورد راهبر عالی

چهار کارت قدیمی بالای داشبورد:
- درخواست دسترسی
- مجوز منتظر تصمیم
- هشدار حل‌نشده
- مصوبه نیازمند توجه

به شکل فعلی حذف شوند.

«درخواست دسترسی» و «مجوزهای سیستمی از راهبر» در منطق فعلی کانون موضوعیت ندارند.
هماهنگی‌ها و اخذ نظر راهبر عمدتاً حضوری/خارج سامانه است.

قسمت بالای Dashboard باید به یک Summary مدیریتی ساده تبدیل شود و چهار محور داشته باشد:

الف) وضعیت خانواده‌های تحت حمایت
- تعداد خانواده‌های فعال
- توزیع A/B/C/D
- تعداد خانواده‌های دارای فوریت «فوری»
- تعداد ارزیابی‌های ناقص یا نیازمند تکمیل اطلاعات

ب) هشدارهای مهم و بحرانی
- بحرانی
- خیلی مهم
- Escalated
- هشدارهای باز
- کلیک روی Summary → All Alerts View

ج) وضعیت گروه‌ها
- تعداد گروه‌های فعال
- تعداد گروه‌هایی که خانواده دارای هشدار بحرانی دارند
- تعداد گروه‌های دارای ارزیابی/بازبینی معوق
- در آینده امکان نمایش گروه فاقد سرگروه یا دارای کمبود ظرفیت

د) گزارش‌ها و پایش
- یک ورودی واضح به ماژول گزارش‌های مدیریتی
- این کارت لزوماً Counter ندارد.

Dashboard نباید Activity Feed پر از انتقال خانواده، تغییر Role یا تغییرات ساختاری نادر داشته باشد.
این موارد در ماژول تخصصی خودشان قابل مشاهده‌اند.

کارت‌ها/ماژول‌های اصلی نقش راهبر در بخش اصلی Dashboard:
- افراد و مسئولیت‌ها
- گروه‌بندی و پایش مددجویان
- مصوبات شورای کانون
- گزارش‌ها و پایش کانون

هشدارها ماژول مستقل پررنگ روی Dashboard نباشند؛ Summary بالا + All Alerts View کافی است.

3. افراد و مسئولیت‌ها

این بخش قبلاً بررسی شده و باید حفظ و اصلاح شود.

- فقط افراد سازمانی کانون در لیست People نمایش داده شوند.
- سرپرست خانوار یا اعضای خانواده صرفاً به دلیل حضور در پرونده خانواده نباید در People دیده شوند.
- اگر یک عضو خانواده مستقلاً نقش سازمانی دارد، آن‌وقت می‌تواند در People نیز حضور داشته باشد.

نقش‌های قابل نمایش:
- سرگروه
- همیار گروه
- عضو شورای کانون
- مدیر اجرایی
- مدیر فنی

SUPREME_GUIDE در UI معمول مسئولیت‌ها نمایش داده نشود.

ساختار Person-centric باشد:
- فهرست افراد
- انتخاب شخص
- نمایش مسئولیت‌های فعلی
- تغییر مسئولیت در همان Person Workspace

برای تغییر Role:
«نوع تغییر» از «مسئولیت» جدا باشد:
- افزودن مسئولیت
- تغییر مسئولیت
- پایان مسئولیت

«پایان مسئولیت» Role نیست.

اگر پایان مسئولیت انتخاب شد، کاربر باید مسئولیت فعلی را انتخاب کند.

Scope:
- همیار گروه و سرگروه → Group Scope
- عضو شورا، مدیر اجرایی، مدیر فنی → سطح کانون
عبارت «سطح سازمان» در UI → «سطح کانون»

History انتصابات باید واقعی باشد و شروع/پایان/تغییر نقش‌ها را نشان دهد.

Note، Warning، Follow-up و Alert از هم تفکیک شوند.
MESSAGE / REMINDER / ALERT خام در UI نمایش داده نشود.

راهبـر Resolver عمومی Alert نیست.

فهرست افراد برای حجم واقعی داده Pagination یا Load More داشته باشد و Headerهای جدول واضح باشند.

4. گروه‌بندی و پایش مددجویان

- سرگروه
- دارای موارد نیازمند توجه

فیلترهای ریز و متعدد مانند تحقیق معوق، بازبینی معوق، هشدار و حداقل میانگین امتیاز صفحه اصلی را شلوغ نکنند.

کلیک روی «موارد نیازمند توجه» → نمای دسته‌بندی‌شده همان گروه.

فرمول امتیاز نهایی:
Final Score =
مجموع امتیاز حوزه‌های Applicable
÷
مجموع وزن حوزه‌های Applicable
× 100

N/A:
- اگر یک حوزه واقعاً قابل‌اعمال نیست، از مخرج حذف شود.
- وزن‌ها به‌صورت ریاضی Normalize شوند؛ بازتوزیع دستی وزن لازم نیست.

Zero / Unknown / N/A را هرگز یکی نکن:
- موضوع Applicable ولی بدون مشکل → 0
- اطلاعات نامشخص → Unknown / Incomplete
- واقعاً غیرقابل‌اعمال → N/A

Unknown هرگز صفر محسوب نشود.

اگر حوزه Applicable ناقص است، ارزیابی نهایی قطعی نشود و وضعیت:
«موقت / نیازمند تکمیل اطلاعات»
داشته باشد.

Final Assessment فقط وقتی نهایی شود که همه حوزه‌های Applicable تکمیل شده باشند و Critical Question الزامی Unknown نداشته باشد.

امتیاز داخلی با Precision مناسب ذخیره شود، UI عدد خوانا نشان دهد.

Thresholdهای A/B/C/D Data-driven و Versioned باشند.

A: 75–100
B: 55–<75
C: 30–<55
D: <30
اما این Thresholdها باید Configurable باشند و در کد Hardcode پراکنده نشوند.

Urgency مستقل:
- فوری
- ضروری
- مهم
- غیرفوری

Critical Flag مستقل از Score و Level باشد.

11. هشدار، اعلان، Reminder و Critical

سه Entity مستقل:
- Notification
- Reminder
- Alert

Critical Flag خودش Alert نیست؛ Rule Trigger است.

Severity Alert:
- پیگیری
- مهم
- خیلی مهم
- بحرانی

Lifecycle:
OPEN
→ ACKNOWLEDGED
→ IN_PROGRESS
→ RESOLVED

Escalation ویژگی جداست.

مشاهده Alert هرگز Resolve نیست.

Resolve فقط با:
- اقدام انجام‌شده
- نتیجه
- تاریخ
- Actor
- پیوست در صورت نیاز

هر Alert عملیاتی Owner داشته باشد.

Owner پیش‌فرض خانواده/ارزیابی:
سرگروه

راهبـر Observer / Escalation Recipient است، نه Resolver عمومی.

Dedup:
family_id + member_id(if applicable) + rule_code

Trigger تکراری → Alert جدید نسازد؛ Alert موجود Update شود.

Trigger که دیگر Detect نمی‌شود → خودکار Resolve نکند؛
فقط Trigger No Longer Detected ثبت شود تا Owner نتیجه واقعی را ثبت کند.

هر مصوبه نهایی که بعداً در Workflow مدیر اجرایی ثبت می‌شود، خودکار به این آرشیو اضافه شود.

قابلیت‌ها:
- Full-text Search
- Keyword Search
- جست‌وجو با نام اشخاص
- فیلتر تاریخ/بازه
- موضوع/دسته
- وضعیت
- مسئول/مجری در صورت وجود
- Sorting
- مشاهده جزئیات و پیوست

هر مصوبه حداقل:
- شماره/شناسه خوانا
- تاریخ
- عنوان
- متن تصمیم
- افراد مرتبط
- مسئول/مجری در صورت وجود
- وضعیت
- پیوست
- History

مصوبه نهایی بدون Audit و History بی‌ردپا ویرایش/حذف نشود.

هیچ Workflow تأیید عمومی برای راهبر نساز.
اگر در آینده Rule مشخصی مثل آستانه مالی تعریف شد، آن یک Feature جدا خواهد بود.

15. گزارش‌ها و پایش کانون

این بخش باید از نو از حالت Generic Data Explorer / Database Viewer خارج شود.

هدف:
«نمای مدیریتی کانون برای راهبر»

چهار حوزه نهایی:

الف) خانواده‌ها و نیازها
ب) حمایت‌ها
   - موردی
   - مستمر
ج) گروه‌ها و ظرفیت اجرایی
د) طرح‌های جمعی

گزارش حامی خروجی طرح‌های جمعی است، نه ماژول اجرایی مستقل.

15.1 خانواده‌ها و نیازها

شاخص‌های بالا:
- خانواده فعال
- سطح A
- سطح B
- فوریت فوری
- پرونده نیازمند بازبینی
- خانواده دارای هشدار مهم/بحرانی

توزیع A/B/C/D:
تعداد + درصد

حوزه‌ها:
- معیشت
- سلامت
- مسکن
- آسیب‌پذیری
- آموزش

برای هر حوزه:
- تعداد خانواده دارای نیاز مؤثر
- تعداد موارد شدید/قابل توجه

فوریت مستقل از A/B/C/D.

وضعیت پرونده:
- به‌روز
- نیازمند بازبینی
- داده ناقص
- بازبینی معوق

تغییر وضعیت خانواده:
مقایسه دو Assessment معتبر آخر:
- بهبود
- بدون تغییر معنادار
- تشدید نیاز

جدول:
- خانواده
- گروه
- سطح نیاز
- فوریت
- حوزه‌های اصلی نیاز
- وضعیت پرونده
- هشدار

15.2 حمایت‌های موردی

شاخص‌ها:
- خانواده‌های برخوردار
- تعداد حمایت
- مجموع ارزش
- میانگین ارزش
- خانواده‌های دارای بیش از یک حمایت در بازه

تحلیل:
- نوع حمایت
- گروه
- زمان
- پراکندگی حمایت
- ارتباط با Level A/B/C/D

حمایت غیرنقدی:
ارزش ریالی قابل ثبت باشد و مشخص باشد:
- واقعی/فاکتور
یا
- برآوردی

Workflow تحویل و Log اجرایی در گزارش راهبر نمایش داده نشود.

15.3 حمایت‌های مستمر

مقرری زیرمجموعه این بخش است.

شاخص‌ها:
- خانواده دارای حمایت مستمر فعال
- تعهد ماهانه
- پرداخت‌شده در بازه
- معوقات
- پرونده‌های دارای معوق

انواع:
- مقرری
- کمک دوره‌ای درمان
- کمک مستمر معیشتی
- سایر

یک نمودار ساده:
تعهد ماهانه در برابر پرداخت واقعی

ریز تک‌تک پرداخت‌ها در جدول اصلی نمایش داده نشود.

15.4 گروه‌ها و ظرفیت اجرایی

هیچ Ranking یا Performance Score ساخته نشود.

هدف:
تشخیص نیاز احتمالی به تقویت.

شاخص‌ها:
- گروه فعال
- خانواده‌های تحت پوشش
- گروه‌های دارای فشار بالاتر از ظرفیت معمول
- گروه‌های دارای بازبینی معوق

جدول:
- گروه
- سرگروه
- همیاران
- خانواده‌ها
- A/B
- موارد فوری
- بازبینی معوق
- وضعیت ظرفیت

وضعیت:
- مناسب
- نیازمند توجه
- نیازمند تقویت

دلیل وضعیت شفاف نمایش داده شود.
هیچ Black-box Score ساخته نشود.

عوامل:
- نسبت خانواده به همیار
- تعداد A/B
- موارد فوری/بحرانی
- بازبینی معوق
- تمرکز چند مسئولیت روی یک فرد

تمام مسئولیت‌ها افتخاری‌اند.
این گزارش برای قضاوت افراد نیست؛ برای دیدن محل تمرکز مسئولیت و نیاز به تقویت است.

15.5 طرح‌های جمعی

برای هر طرح:
- عنوان
- مناسبت/هدف
- تاریخ
- خانواده‌های برخوردار
- تعداد بسته/خدمت/سهم
- ارزش کل
- منابع تأمین
- گروه‌های تحت پوشش
- وضعیت طرح

جزئیات اجرایی:
- عدم تحویل
- جایگزین
- علت عدم تحویل
- وضعیت تحویل فردی
- پیگیری عملیاتی

در گزارش راهبر و گزارش حامی نمایش داده نشوند.
اینها متعلق به Workflow اجرایی گروه‌ها هستند.

گزارش حامی:
- نام طرح
- مناسبت
- تاریخ اجرا
- تعداد خانواده بهره‌مند
- تعداد بسته/خدمت
- ارزش کل
- محدوده پوشش
- نام حامی در صورت نیاز
- توضیح کوتاه نتیجه

ضمیمه اختیاری:
لیست خانواده‌های برخوردار بدون اطلاعات حساس غیرضروری.

گزارش حامی مستقیماً از داده نهایی طرح تولید شود؛ ورود مجدد اطلاعات ممنوع.

17. Excel / PDF / Print

Excel کار می‌کند و باید حفظ شود.

- فارسی

- فیلترهای اعمال‌شده

Print:

- فارسی
- Page Break مناسب
- Portrait/Landscape متناسب
- بدون ستون فنی

18. محدوده این مرحله

تمرکز این مرحله فقط روی کامل‌کردن و بازبینی اساسی نقش SUPREME_GUIDE و زیرساخت‌های Shared مورد نیاز آن است.

داشبورد کامل سرگروه را در این مرحله نساز.
بعد از پایان و تأیید نقش راهبر، مرحله بعد طراحی و توسعه نقش سرگروه خواهد بود.

با این حال، زیرساخت‌های مشترک مثل:
- Assessment Versioning
- Scoring Rules
- Alert Engine
- History/Audit
- Reporting Backend
باید طوری ساخته شوند که در مرحله سرگروه قابل استفاده باشند و دوباره‌کاری ایجاد نشود.

19. تست و معیار پذیرش

حداقل این موارد را با تست Backend و Browser پوشش بده:

- People فقط افراد سازمانی را نشان دهد.
- اعضای خانواده بدون Role سازمانی وارد People نشوند.
- Role Change و End Responsibility History صحیح بسازند.
- Family Transfer موفق باشد و History مبدأ/مقصد را نشان دهد.
- هیچ Enum خام انگلیسی در صفحات اصلی راهبر دیده نشود.
- Seedها فارسی باشند.
- Dashboard Summary از داده واقعی تغذیه شود.
- N/A / Zero / Unknown در Scoring درست رفتار کنند.
- آموزش بدون عضو مشمول → N/A و Normalize صحیح.
- سلامت بدون مشکل → 0، نه N/A.
- Assessment ناقص → Final نشود.
- Snapshot تاریخی بعد از تغییر اطلاعات خانواده تغییر نکند.
- Alert Duplicate ساخته نشود.
- Alert با مشاهده Resolve نشود.
- Resolve بدون Action + Result مجاز نباشد.
- Guide نتواند Alert عمومی را مانند Resolver عملیاتی ببندد.
- Council Archive Search/Filter کار کند.
- Reports Drill-down درست به داده مربوط برسد.
- Report UI هیچ JSON/UUID/Raw Enum نشان ندهد.
- Excel خروجی قابل استفاده تولید کند.
- PDF خراب در UI نمایش داده نشود تا زمانی که اصلاح شود.
- Responsive/Desktop tableها متن عمودی و شکسته نداشته باشند.

20. شیوه اجرا و تحویل

قبل از تغییر، Implementation موجود را Audit کن و مشخص کن چه چیزهایی قابل استفاده‌اند و چه چیزهایی باید اصلاح یا جایگزین شوند.

از Patchهای سطحی که Architecture غلط فعلی را حفظ می‌کنند پرهیز کن.

اما Featureهای سالم موجود را بی‌دلیل بازنویسی نکن.

Database فعلی را حفظ کن.

در پایان:
- Migrationهای لازم
- Seed اصلاح‌شده
- Source کامل
- تست‌های کامل
- Build موفق
- گزارش مختصر ولی دقیق از:
  • تغییرات انجام‌شده
  • Route/APIهای جدید یا اصلاح‌شده
  • Migrationها
  • تست‌ها و تعداد PASS/FAIL
  • موارد Deferred
  • مواردی که عمداً طبق Specification حذف شدند
ارائه کن.

یک ZIP کامل و قابل اجرای پروژه تحویل بده.

مهم:
اگر در Specification بالا بین UI فعلی و تصمیم‌های نهایی تعارض وجود دارد، تصمیم‌های نهایی این متن مقدم‌اند.
اگر برای یک قابلیت Workflow واقعی تعریف نشده، چیزی از خودت اختراع نکن.
اگر موردی مبهم است، ابتدا منطق کسب‌وکار را با تصمیم‌های فوق تطبیق بده و ساده‌ترین راه سازگار با آنها را اجرا کن.
